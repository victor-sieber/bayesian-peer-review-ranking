# Reproducing the analysis

This document describes how to reproduce the analyses and figures reported in

**How Much Can Sparse Peer Review Tell Us? Bayesian Ranking, Outcome Sensitivity, and Review Design for Research Funding Decisions.**

## 1. Clone the repository

Clone the repository and enter its root directory:

```bash
git clone <REPOSITORY-URL>
cd evaluation-data
```

Replace `<REPOSITORY-URL>` with the URL of the Git repository.

## 2. Obtain the analytical dataset

The row-level analytical dataset is pseudonymized and is not stored directly
in this Git repository.

Following final CRS review and authorization, the dataset is intended to be
archived separately on Zenodo.

**Zenodo:** link to be added

Download the pseudonymized analytical CSV from the Zenodo record. If necessary,
rename the downloaded file and place it inside the cloned repository at the
exact path

```text
data/evaluation_anonymized.csv
```

All analysis scripts that use the row-level data expect this path.

The existing filename is retained for compatibility with the analysis
workflow. The data are more accurately described as pseudonymized because the
re-identification key is stored separately and is not part of this repository,
the analytical dataset release or the analysis workflow.

After adding the dataset, the relevant part of the repository structure should
look like

```text
evaluation-data/
├── analysis/
├── data/
│   ├── README.md
│   └── evaluation_anonymized.csv
├── figures/
├── report/
├── results/
├── README.md
└── REPRODUCIBILITY.md
```

## 3. Software requirements

The analysis was developed using R and JAGS.

Required external software:

- R
- JAGS
- Quarto, if the technical report is to be rendered

Package and software information for the final analyses is recorded in the
`session_info.txt` files stored under `results/`.

From the repository root, install the required R packages with

```r
source("analysis/00_install_heyard_dependencies.R")
```

The model-fitting scripts attempt to locate the JAGS executable automatically.
JAGS must therefore either be available on the system `PATH` or installed in
the standard Apple Silicon Homebrew location `/opt/homebrew/bin/jags`.

If JAGS cannot be located, the fitting scripts stop with an explanatory error
message.

## 4. Run the analyses

The analyses should be run from the repository root.

The scripts should be run in the order shown below because several downstream
analyses use posterior objects or derived outputs created by earlier scripts.

```r
source("analysis/01_fit_v0_heyard_reference.R")
source("analysis/02_fit_v1_cross_classified.R")
source("analysis/03_compare_v0_v1.R")

source("analysis/04_validate_v1.R")
source("analysis/04b_fit_v1_prior_sensitivity.R")
source("analysis/04c_investigate_v1_disagreement.R")

source("analysis/05_analyze_criteria.R")
source("analysis/06_fit_compare_v1_criterion_average.R")

source("analysis/06a_visualize_review_graph.R")
source("analysis/07_single_review_design.R")
source("analysis/08_visualize_review_design_results.R")
source("analysis/09_compare_review_allocation_policies.R")
```

In particular, scripts `01` and `02` create the fitted V0 and V1 posterior
objects used by subsequent analyses.

Script `04b` performs a separate prior-sensitivity fit of V1, while script `06`
performs a separate V1 fit using the equal-weight criterion-average outcome.

Script `07` uses the fitted baseline V1 posterior object for the single-review
design calculation, and scripts `08` and `09` build on the review-design
analysis and its derived outputs.

The scripts have different computational costs. In particular, the Bayesian
model-fitting scripts use MCMC and may take substantially longer than the
downstream summary and visualization scripts.

## 5. Generated posterior objects

Some model-fitting scripts create local `.rds` objects containing posterior
samples or fitted model objects.

These files are intentionally excluded from Git because of their size.

They can be regenerated by rerunning the corresponding model-fitting scripts
and are then used by downstream analyses.

The principal generated posterior objects include the V0 fit, the baseline V1
fit, the prior-sensitivity V1 fit and the criterion-average V1 fit.

## 6. Derived outputs

Derived numerical summaries are written under

```text
results/
```

and generated figures are written under

```text
figures/
```

These outputs document the numerical results used in the technical report.

The repository also contains selected report-specific copies of figures under

```text
report/figures/
```

for rendering the Quarto report.

The main analysis scripts write their outputs into separate subdirectories so
that results from different model specifications and analysis stages remain
distinguishable.

## 7. Render the technical report

After the required analyses and figures are available, render the technical
report from the repository root with

```bash
quarto render report/technical-report.qmd
```

The report source is

```text
report/technical-report.qmd
```

and the rendered PDF is

```text
report/technical-report.pdf
```

Depending on the Quarto configuration, an HTML version may also be generated.

## 8. Reproducibility notes

Fixed random seeds are used where stochastic computation is involved.

The Bayesian model-fitting scripts document the MCMC settings, initialization
procedure and random seeds used for the final analyses.

The single-review design calculation evaluates all currently unobserved
reviewer--proposal assignments and averages the resulting design-criterion
reductions across posterior draws from the fitted baseline V1 model.

The random allocation benchmark in the limited-review policy comparison also
uses a fixed simulation seed.

The review-design calculations intentionally do not incorporate reviewer
expertise, conflicts of interest, availability or other operational assignment
restrictions because these variables were not available for the present
analysis.

The committed `session_info.txt` files under `results/` record the R and package
versions used for the corresponding analyses.
